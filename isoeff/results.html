Marginal efficiency: what the last step bought

For a step from P′ to P: (S(P) / S(P′)) / (P / P′), the share of the ideal extra speed-up the extra ranks delivered. It reacts sooner than E, which averages over all ranks so far. The dotted line is the marginal rule.

Marginal efficiency of the step to P (%)

Serial fraction implied by each P (Karp–Flatt)

e = (1/S − 1/P) / (1 − 1/P): the serial fraction that Amdahl's law would need to explain each measured speed-up. Flat: a fixed serial part. Rising with P: a cost that grows with the number of ranks, such as communication or waiting for the slowest rank. Falling with N: the fixed costs matter less for bigger problems, which is what makes growing N work.

    How the capacity numbers were made, and what they leave out
    
    
      
  • isoeff/controller.py (capacity mode) ran each version as a chain of LSF jobs on whole reserved nodes. Every job was one MPI run of — time steps; it counts as finished in time when it completed all of them within its own time limit (the —-minute walltime minus two minutes for saving). Merge radius — pc: every run at one N follows the same trajectory, merges included.
    • 
      
  • The rule, replayed from the runs before every job: at each P, N grows along a grid (×√2) until the run no longer finishes in time. Then the next P is timed on the largest N the previous P managed; the step is kept when its marginal efficiency reaches the rule, otherwise it is measured once more and the campaign stops.
    • 
      
  • There is no serial run: the code's correctness is checked separately, and speed-ups are only taken between MPI runs. Each run is its own job, so the two runs of a step can land on different nodes, which differed by up to about 16 %; a failing step is therefore measured twice.
    • 
      
  • The numbers are embedded in this file by isoeff/make_page.py from each campaign's capacity.csv, cap_points.csv, thresholds.csv and decisions.log.

    How the numbers were made, and what they leave out
    
    
      
  • isoeff/controller.py ran each version as a chain of LSF jobs on whole reserved nodes (—). Every job measured one point: the serial program on N stars, then — MPI repeats with P ranks on the same node.  Merge radius — pc.
    • 
      
  • The rule, replayed from the measurements before every job: step P up through the P list while the step is cost-effective; at a threshold, multiply N by — and test the same step again. A failing step was measured a second time before it was accepted.
    • 
      
  • Speed-ups are medians over the jobs of a point, each job's speed-up taken against its own serial run on the same node, because nodes of the same type differed by up to about 16 %. The serial program always uses the v1 force kernel, so versions with a faster kernel (--tile-rows) report the kernel gain inside S.
    • 
      
  • The numbers are embedded in this file by isoeff/make_page.py from each campaign's points.csv, thresholds.csv, decisions.log and results.csv.
    • 
      
  • Not covered: N beyond what a serial step allows in one job (about 16,000 stars at 7 minutes), start-up and loading (only the step loop is timed), and correctness (each version was validated separately with batch.sh MODE=validate).
