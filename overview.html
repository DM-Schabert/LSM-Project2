Results overview: Amdahl, communication and memory

Everything measured on the scaling of v1, the communication schemes and the memory per rank, on one page, with links to the detail pages. In short: v1 (Allgather, blocking) stays the best scheme, and neither the network nor the memory is the limit. The computation per step is.

Results

Amdahl (details)

  • At N = 5 000, S(24) = 23.3 (97 %). At N = 50 it stops at S(24) = 9.1 (38 %).
  • About 0.1 ms per step does not get faster with more ranks, whatever N is. At small N that is a large share: the uneven split of the stars, the Allgather latency and the fixed Python work per step.
  • Every launch costs 1.80 s plus 28 ms per rank before the first step.

Communication schemes, C0 to C4 (details)

  • The network is not the limit. The Allgatherv is 0.12 % of a step at N = 20 000 and P = 48, and at most 0.7 % from N = 5 000 on.
  • The second node pays off from N ≈ 1 000 on. From P = 24 to 48, v1 gets ×1.76 (N = 1 000) to ×1.98 (N = 20 000) faster. At N = 50 every scheme gets slower.
  • v1 is the best or equal from N = 1 000 on. 2D is better only at N = 50 (14 % on one node, 6 % at P = 48). The ring collapses at small N, because it calls the force kernel P times per step at about 70 µs per call.
  • At large N the differences between the schemes come from the force kernel, not from the bytes sent (not followed up).

Overlap in depth (details)

  • On one node nothing is hidden, at any message size. Through shared memory the CPU copies the data, and only while the program is inside an MPI call.
  • Across two nodes about 40 % is hidden from 64 KB on, because the network card moves part of the data by itself.
  • Testall between the tiles moves the copy instead of hiding it: the time in Waitall drops, the computation gets longer by the same amount, and the exchange is slower in net.
  • Irecv + Isend + Waitall cost 8–10 µs more per exchange than one Sendrecv. That is the loss of the overlap ring at N = 50.
  • Even a perfect overlap could have saved at most 0.57 % of a step at N ≥ 5 000.

Memory in depth (details)

  • 187 MB per rank before any star (Python, NumPy, pandas, matplotlib, mpi4py). The second node adds 76 MB per rank (the network transport).
  • Every rank holds the whole catalogue, 85–88 B per star, the same for v1, ring and 2D. The ring and 2D save only after the peak.
  • Rank 0 sets the limit: pandas needs 321 B per star more while it reads the CSV. At 589 993 stars rank 0 needs 418 MB, the other ranks 275 MB.
  • Without tiles memory would come first: one tile for a rank's whole block fills 1 GB per rank from about 16 000 stars at P = 24.
  • The kernel needs 79 B per pair of a tile, not 56: the previous tile's arrays stay alive until the next tile replaces them. A del at the end of the tile loop would bring it back to 56 B.

Side findings

  • One fast node: n-62-21-75 is 12 % faster than the other nodes with the same CPU. The communication pages correct every time for the slowest node of its run; after that, C3 repeats C2 within 1–2 %.
  • P = 32 (24 + 8 ranks): at N ≥ 5 000 the Allgatherv is 4–6 times slower than at P = 48 (about twice at N = 1 000), most likely because Open MPI picks another algorithm (not checked).
  • LSF's "Max Memory" misses short peaks: it samples every few seconds and saw 2.5 GB of a real peak of about 20 GB.

Expectations that did not hold

Every detail page wrote its expectations down before measuring. These did not hold, and they are worth keeping in the report:

  • C0's prediction for the ring at N = 50 was off by a factor of about 90. C0 timed only the messages, but the ring's cost is the P kernel calls per step.
  • Overlap across two nodes was expected to gain; it measured 0 to −10 %.
  • "2D scales further" (from the project description) does not hold for N ≤ 20 000 and P ≤ 48.
  • "Small messages are hidden, large ones are not" was wrong: on one node nothing is hidden, across nodes about 40 % of the large ones. The rule for Testall measured the time in Waitall rather than the net time, so its "yes" is misleading; the overlap page adds the net saving.
  • Kernel memory is 79 B per pair instead of 56. Explained: the previous tile's arrays stay alive.
  • LSF's "Max Memory" was expected to match the sum over the ranks; it missed the short peaks.

Open

  • Why the kernel slows down with every core busy. At N = 5 000 and P = 24 the summed kernel time of all ranks is 1.29 times that of one rank for v1, 1.37 for 2D and 1.63 for the ring. Most likely the tiles' temporaries compete for the shared cache. This would decide whether smaller tiles make the program faster. Not followed up.
  • P = 32: which Allgatherv algorithm Open MPI picks there.
  • Overlap at 4 MB: why the share hidden across nodes drops again (a UCX protocol detail, not needed for the conclusion).
  • Memory over many steps: a leak would only show over thousands of steps. The peak_memory_mb of the 10 000-step isoefficiency runs could answer this without a new job.
